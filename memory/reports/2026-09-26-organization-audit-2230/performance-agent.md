# דוח סוכן ביצועים — GoNorth

תאריך: 26.09.2026. בדיקות חיות בשעות 22:37–22:41, שעון ישראל. תחום: ביצועי תבניות פנים, תמונות, משאבי צד לקוח ועלות הרחבות. ביקורת בלבד; לא שונו האתר, המטמון, התוספים או מסד הנתונים.

## TL;DR

דף הבית כבר עבר בהצלחה את תיקון #72: מדידות Google PSI הסופיות מהיום הן **96, 99, 99 במובייל**. אין הצדקה לפתוח שוב את אותה משימת אופטימיזציה. ההזדמנות הבאה היא בעמודי הפנים: מדגם של ארכיון, מקום וכתבה כולל כ־1MB של CSS מקומי לאחר פריסה, וגם כתבת תוכן טוענת רכיבי מסחר ו־GeoDirectory. בשני קבצים סטטיים משמעותיים אומת היעדר דחיסה והיעדר Cache-Control בתגובה, בעוד HTML וקובצי Autoptimize דינמיים כן נדחסים. כדאי לטפל באספקת נכסים ובטעינה לפי תבנית לפני הוספת מפות, גלריות ומודולי הזמנה. יש להוסיף מדידת משתמשים אמיתיים; ציוני מעבדה אינם מוכיחים שכל האתר עומד ב־Core Web Vitals.

## היקף, שיטה וגבולות הראיות

נקראו הגדרת התפקיד, wp-performance, זיכרון העבודה ודוח #72 עד **התיקון האחרון**. נבדקו שלוש כתובות ציבוריות: [ארכיון מקומות](https://gonorth.co.il/places/), [קיאק־כנרת — מקום 423](https://gonorth.co.il/places/%d7%a7%d7%99%d7%90%d7%a7-%d7%9b%d7%a0%d7%a8%d7%aa/), [מדריך סיורים וקיאקים — עמוד 436](https://gonorth.co.il/tours-kayaks-north-israel/). הארכיון והכתבה נפתחו גם בדפדפן, לבדיקת המשאבים והתמונה שבחר בפועל.

curl ביצע GET יחיד לכל כתובת עם תמיכה בדחיסה, ללא פרמטר עוקף מטמון. לאחר מכן נאספו קובצי CSS/JS ותמונות first-party מתוך HTML. הסכומים הבאים אינם waterfall מלא: הם אינם כוללים גופנים שאליהם CSS מפנה, צדדים שלישיים, חלופות srcset שלא הורדו או משאבים שנוצרים מאוחר. משקל נכס שנאסף דרך fetch הוא לאחר פריסה; אין להציג אותו כמשקל ההורדה הדחוסה בדפדפן. בדיקת DOM הצביעה על WebP בכרטיסי הארכיון גם כשמקור HTML מפנה ל־JPEG; לכן אין להסיק שכל המבקרים מקבלים JPEG.

## ממצאים

| תבנית | HTTP | TTFB בבקשה היחידה | HTML דחוס | CSS מקומי לאחר פריסה | JS מקומי לאחר פריסה |
|---|---:|---:|---:|---:|---:|
| ארכיון | 200 | 876ms | 134KB | 1,025KB | 445KB |
| מקום 423 | 200 | 872ms | 139KB | 1,041KB | 450KB |
| כתבה 436 | 200 | 849ms | 134KB | 1,041KB | 445KB |

KB בטבלה הוא אלף בתים, בעיגול. HTML לפני דחיסה נע בין 477KB ל־498KB. התוצאות הן **חיות**, אך TTFB כולל את רשת המדידה, DNS וחיבור: הוא מעל יעד הפרויקט 600ms במדגם זה, ואינו הוכחה לזמן PHP איטי או לפסילת CWV. דרושות חזרות מאותו אזור ובאותו פרופיל.

**1. תבניות פנים עדיין מקבלות מעטפת כבדה.** נמצאו 14–15 תגי stylesheet חיצוניים. רכיב CSS יחיד של Autoptimize בגרסת AyeCode UI שוקל 515,736 בתים לאחר פריסה. בכתבה מופיעים Bootstrap, GeoDirectory, jQuery Migrate, add-to-cart, WooCommerce ו־order-attribution. אלה מועמדים לבדיקת נחיצות, לא הוכחה שכל אחד ניתן להסרה: מסננים, נגישות ורכיבים משותפים עלולים להיות תלויים בהם. קובץ הכותרות והרשימות המלאות נמצאים בראיות המקומיות.

**2. אספקת קבצים סטטיים ראויה לתיקון ממוקד.** Gutenberg CSS ‏140,886 בתים ו־Bootstrap JS ‏136,517 בתים חזרו ב־200 ללא Content-Encoding, גם ב־GET וגם ב־HEAD עם בקשת דחיסה. לא נמצא Cache-Control; כן נמצאו ETag ו־Last-Modified. לפיכך אין לומר שאין כלל מטמון דפדפן, אלא שחסרה בתגובות מדיניות מפורשת ונצפתה העברה ללא דחיסה. לעומתם HTML החי וקובצי Autoptimize מסוג PHP חזרו עם gzip. ההבחנה מצביעה על מסלול שירות סטטי בשרת כמועמד לבדיקה; אין גישה לתצורת Nginx להוכחת הסיבה.

**3. כמה יסודות תמונה כבר קיימים.** תמונת המקום הראשית מכילה width/height, srcset, ‏eager ו־fetchpriority=high; תמונת הכתבה מכילה מידות, srcset ו־high. מקור תמונת הכתבה הוא WebP ‏415,390 בתים, ובדפדפן נבחרה חלופת 1536×864 לתצוגה ברוחב כ־1265px. תמונת המקור של קיאק־כנרת היא JPEG ‏302,733 בתים; אין זו מדידת משקל התמונה הנבחרת בכל מסך. כרטיסי הארכיון כוללים lazy ומידות. אין צורך להציע התקנת תוסף תמונות נוסף לפני בדיקת התוצאה שכבר מספקת התשתית.

**4. דף הבית הוא הצלחה מתועדת מהיום.** הראיות האחרונות בדוח #72 הן Google PSI רשמי במובייל: 96/99/99, ‏LCP ‏2.4/1.4/1.5 שניות ו־CLS ‏0.042 בשלוש הרצות. ערכי 59, 86 או 95/96/94 הם שלבים קודמים, ולא מצב נוכחי. ציון דסקטופ 100 שייך לשלב מקומי מוקדם יותר; לא נערכה כאן מדידת דסקטופ רשמית חדשה.

**5. חסרה תמונת שדה מאומתת בדוח זה.** אין כאן נתוני CrUX, ‏INP של משתמשים, Search Console או התפלגות מכשירים. לפי התיעוד העדכני, יעדי CWV הם LCP עד 2.5 שניות, INP עד 200ms ו־CLS עד 0.1 באחוזון 75. TBT ממעבדה אינו INP, ו־FID שבסקיל הישן אינו המדד הנוכחי. [Web Vitals](https://web.dev/articles/vitals).

## תשובות לתשע שאלות ההנהלה

1. **האם לעדכן עיצוב?** כן, באופן נקודתי: כרטיסים בעלי יחס תמונה עקבי, מקום שמור לרכיבי טעינה, וכותרת שימושית שמופיעה מוקדם בעמוד. אין ממצא ביצועים המצדיק החלפת מותג או שכתוב האתר. את השיפור הראשון יש לבצע באספקת CSS/JS של עמודי הפנים, גם אם החזות נשארת דומה.
2. **מה לשפר בחוויית המשתמש?** למדוד ולשפר את זמן ההגעה לחיפוש ולפרטי ביקור, תגובה למסנן ופתיחת ניווט במובייל. להשאיר תוצאה וניווט שמישים בזמן שמפה או גלריה נטענות. זו המלצת תכנון; לא נמדדה כאן תקיעת מסנן מסוימת.
3. **איזה תוכן להוסיף?** בלוק HTML קצר של “לפני שיוצאים”, קישורי ניווט ומידע מאומת נגישים מהר יותר ממידע שקיים רק בתמונה או באקורדיון כבד. אפשר להרחיב מדריכים קיימים בתוכן עריכתי מועיל ללא SDK חדש. בחירת הנושאים תלויה בסוכן התוכן וה־SEO.
4. **איך לשפר Google וחיפוש AI?** להשאיר את התוכן העיקרי והקישורים נגישים ב־HTML, להגן על זמינות ומהירות ולהימנע מתלות בצ'אט לשם קבלת מידע בסיסי. Google מציין שאין דרישות טכניות מיוחדות נוספות להופעה בתכונות AI מעבר ליסודות החיפוש; אין הבטחת מיקום כתוצאה מציון מהירות. [Google AI features](https://developers.google.com/search/docs/appearance/ai-features).
5. **האם להוסיף תמונות?** כן כשיש ערך: כניסה, חניה, מרחב האירוח והמסלול עצמו, בכפוף לזכויות ולאימות. לפי snapshot המשותף לכל 109 המקומות יש featured_media, ול־19/21 פוסטים יש תמונה ראשית; חסרונה ברשומות 431/432 הוא תור בדיקה, לא הוכחה שאין תמונה בגוף. להוסיף גלריה קטנה ומדורגת, לא עשרות תמונות בפתיחה. תמונת AI אווירתית אינה תיעוד עובדתי של מקום.
6. **אילו מקומות להוסיף?** אין אילוץ ביצועים שמצדיק בחירת עסק מסוים. כדאי להרחיב אזורים חסרים לפי דוח הליסטינג, לאחר סינון כפילויות ואימות פעילות, ולדרוש מכל רשומה ערכת תמונות בגודל מתאים. המלצתי היא אצווה קטנה של 5–10 רשומות למדידת השפעה; איני מאשר כאן עסק חדש שלא נחקר.
7. **קטגוריות חדשות?** “נגיש”, “מקורה” ו“מתאים לילדים” עדיפים תחילה כמאפיינים או מסננים מאומתים, אם זו אכן משמעותם. לא לטעון מראש את כל תוצאות כל ציר סינון ולא ליצור אלפי צירופי URL. עמוד קטגוריה נוסף מוצדק לפי מלאי ותועלת תוכן, ולא כדי להצדיק תוסף נוסף.
8. **מודולים חדשים?** עדיפות למפה לפי בקשה, שמירת מקומות מצומצמת והשוואת מספר מקומות ב־HTML. מפות חיות, מנוע הזמנות, סרטונים וצ'אט מוסיפים עלות העברה, הרצת JS ותלויות. יש לטעון SDK רק בהקשר שבו משתמשים בו ולמדוד את המסע לאחר הפעלתו.
9. **תוספות נחוצות?** ניטור ביצועים לפי תבנית, תקציב משאבים ושער בדיקה לפני פרסום. לא נמצא צורך בתוסף מטמון או מיניפיקציה חדש; קודם מאמתים את ההגדרות והנכסים שכבר מוגשים.

[Performance budgets](https://web.dev/articles/performance-budgets-101).

## תוכנית 30/60/90 יום

**עד 30 יום:** למדוד עמודי פנים בתנאים חוזרים, לתקן מדיניות אספקת קבצים סטטיים לאחר גיבוי תצורה, ולמפות תלות של CSS/JS. לשמור את #72 כסגירת עבודה שבוצעה ולתעד בסיס חדש לתבניות פנים. להגדיר תקציבי תמונות יחד עם המעצב.

**עד 60 יום:** לפרוס טעינה מותנית בהדרגה, תחילה בכתבות ואז בארכיון ובמקום, עם בדיקות חיפוש, נגישות ותנועה פנימית. להפעיל ניטור שדה ולבדוק מדגם מובייל אמיתי. להוסיף תמונות לתוכן חסר תוך מעקב אחר משקל נבחר בפועל ולא רק המקור במדיה.

**עד 90 יום:** להחליט על מודולים לפי שימוש ומדידת אינטראקציה; לבדוק מפה לפי בקשה ושמירת מקומות כניסויים נפרדים. להשוות אחוזוני ביצועים ופעולות שימושיות כגון ניווט ופתיחת פרטי מקום בתקופות זהות, תוך ציון שינויי קהל ועונה. לא לייחס שינוי אורגני לביצועים בלבד.

## סיכונים ומגבלות

SSH אינו זמין בהקשר הביקורת; גודל DB, autoload, מצב OPcache ו־cache hit אינם ידועים. לא בוצע ניקוי מסד או מטמון. לא נערכה בדיקת עומס, בדיקת מכשיר חלש או Lighthouse חדש לעמודי הפנים. קובצי CSS גדולים אינם כולם “לא בשימוש” עד בדיקת coverage ותלות. מתן מטמון ארוך ללא גרסת URL יכול להשאיר עיצוב ישן, והסרת Bootstrap או WooCommerce ללא בדיקה עלולה לפגוע ברכיב קיים. יש לשמר lazy loading לתמונות המשך; תיעדוף תמונת LCP הוא דיון נפרד ושכבר מטופל במדגם. [Optimize LCP](https://web.dev/articles/optimize-lcp).
